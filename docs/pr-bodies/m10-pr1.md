**2. P3, P4 and P5 printed no pytest summary because the gate crashed while echoing pytest's
output.** This is **not** the cause from M09b PR 3. There, `pytest | tail && git commit`
swallowed a non-zero exit code. Here the exit code was non-zero, and the gate blocked. All
five red runs of P3, P4 and P5 carry the same traceback:

```
  File "...\pave\cli.py", line 1388, in check
    sys.stdout.write(line)
  File "C:\Python314\Lib\encodings\cp1252.py", line 19, in encode
UnicodeEncodeError: 'charmap' codec can't encode character '\ufffd' in position 19: character maps to <undefined>
```

`check` streams pytest's output through `Popen(..., encoding="utf-8", errors="replace")`
and echoes each line to `sys.stdout`. Under the audit, stdout was redirected to a file on
Windows, where Python's preferred encoding is `cp1252`. Once a failing test printed a line
whose bytes did not decode as UTF-8, `errors="replace"` produced U+FFFD. `cp1252` cannot
encode that character, so the echo raised.

- **The exit 1 in those runs is an uncaught exception, not the gate's decision.** Its
  `error: check failed:` block never printed, and pytest's run ended at the crash.
- **Fail-closed held**, because a crash exits non-zero.
- **What was lost is the teaching:** the failure list and the summary line.
- The P1, P2, P6 and P7 red runs printed no such character and read normally.
- **Not measured in CI.** The workflow runs on a UTF-8 Linux runner, and this was reproduced
  only on the operator's Windows machine with redirected output.

**Proposed debt row, not opened:** the gate's pytest echo crashes on a non-`cp1252`
character when stdout is redirected on Windows, and the report it exists to print is lost.
Owner Platform Engineering. Trigger: the next PR that edits `check` in `pave/cli.py`.
